# **3.4. Quy chuẩn hệ thống ghi vết, định dạng log và kiến trúc module giả lập lỗi** 

Trong phần này, báo cáo trình bày chi tiết về quy chuẩn ghi vết hệ thống (Trace Protocol), cấu trúc dữ liệu của các file log xuất ra nhằm phục vụ công tác giám sát, và kiến trúc của module giả lập lỗi (Fault Injector) để đánh giá khả năng chịu lỗi (resilience) của hệ thống. 

## **3.4.1. Quy chuẩn hệ thống ghi vết (Trace Protocol)** 

Hệ thống ghi vết được thiết kế dựa trên tiêu chuẩn phân tán (distributed tracing) như OpenTelemetry, đảm bảo khả năng theo dõi luồng xử lý xuyên suốt qua nhiều dịch vụ (microservices) khác nhau. 

- **Định danh luồng xử lý:** Mỗi request khi đi vào hệ thống sẽ được gắn một `TraceID` duy nhất. Tại mỗi dịch vụ hoặc node mà request đi qua, một `SpanID` sẽ được tạo ra, trong đó `ParentSpanID` trỏ về tiến trình gọi nó trước đó. 

- **Mức độ sự kiện (Log Levels):** Hệ thống phân loại log thành 5 cấp độ tiêu chuẩn để dễ dàng lọc và thiết lập cảnh báo: 

   - **DEBUG:** Thông tin chi tiết phục vụ quá trình chẩn đoán và phát triển. 

   - **INFO:** Ghi nhận các trạng thái hoạt động bình thường, các mốc giao dịch quan trọng. 

   - **WARN:** Cảnh báo các bất thường có thể xảy ra (ví dụ: phản hồi API chậm) nhưng hệ thống vẫn tiếp tục hoạt động. 

   - **ERROR:** Lỗi xảy ra tại một tiến trình, ảnh hưởng đến một giao dịch nhưng chưa gây sập toàn hệ thống. 

   - **FATAL/CRITICAL:** Lỗi nghiêm trọng khiến dịch vụ bị gián đoạn, cần can thiệp ngay lập tức. 

- **Đồng bộ thời gian:** Tất cả các node trong hệ thống phải được đồng bộ thời gian thực qua giao thức NTP, nhãn thời gian (timestamp) được ghi nhận chuẩn theo múi giờ UTC hoặc ISO-8601. 

## **3.4.2. Định dạng file log xuất ra** 

Để tối ưu hóa việc phân tích tự động, trích xuất dữ liệu bằng các hệ thống quản lý log tập trung (như ELK Stack, Splunk, Datadog), log được xuất ra dưới định dạng **JSON Structed Log** . 

## **Cấu trúc các trường dữ liệu tiêu chuẩn (Log Schema):** 

- `timestamp` : Thời điểm ghi nhận sự kiện (định dạng ISO-8601). 

- `level` : Cấp độ log (INFO, ERROR...). 

- `trace_id` : Mã định danh chuỗi giao dịch phân tán. 

- `span_id` : Mã định danh tác vụ cục bộ tại dịch vụ hiện tại. 

- `service_name` : Tên module hoặc dịch vụ phát sinh log. 

- `message` : Nội dung tóm tắt của sự kiện hoặc lỗi. 

- `metadata` : Khối dữ liệu linh hoạt (JSON object) chứa các thông số ngữ cảnh (User ID, IP, Error Stacktrace, v.v.). 

## **Ví dụ một bản ghi log chuẩn:** 

JSON 

```
{
  "timestamp": "2026-10-31T03:27:15.123Z",
  "level": "ERROR",
  "trace_id": "4b82d4f5c9e210a",
  "span_id": "a9c2b1e3f8",
  "service_name": "payment-gateway",
  "message": "Transaction failed due to external API timeout",
  "metadata": {
    "user_id": "usr_981273",
    "endpoint": "/api/v1/checkout",
    "latency_ms": 5050,
    "error_code": "ERR_EXT_TIMEOUT",
    "stack_trace": "TimeoutException at module.http.client line 142..."
  }
}
```

## **3.4.3. Kiến trúc module giả lập lỗi và ngoại lệ (Fault Injector)** 

Module giả lập lỗi (Fault Injector) được thiết kế theo nguyên lý Chaos Engineering, nhằm chủ động bơm các lỗi kịch bản vào hệ thống trong môi trường kiểm thử (hoặc staging) để kiểm chứng cơ chế tự phục hồi, timeout, và retry của hệ thống. 

## **Các thành phần chính của kiến trúc Fault Injector:** 

1. **Rule Manager (Bộ quản lý luật):** 

   - Tiếp nhận cấu hình từ kỹ sư kiểm thử (qua file cấu hình JSON/YAML hoặc API). 

   - `o` Định nghĩa các tập luật: _Khi nào_ (điều kiện trigger), _Ở đâu_ (dịch vụ nào, endpoint nào), và _Lỗi gì_ (loại lỗi). 

2. **Injector Engine (Động cơ chèn lỗi):** 

   - Thực thi các luật đã được định nghĩa. Nó tính toán xác suất (ví dụ: chỉ giả lập lỗi trên 5% tổng số request) để kích hoạt cơ chế can thiệp. 

3. **Target Hooks / Interceptors (Điểm neo can thiệp):** 

   - Được nhúng trực tiếp vào Application Layer (qua middleware, gRPC interceptors) hoặc Network Layer (qua Service Mesh như Istio). 

   - Thực hiện các hành vi gây lỗi thực tế. 

4. **Telemetry & Metrics (Theo dõi hiệu ứng):** 

   - Đo lường cách hệ thống đích phản ứng (tỉ lệ HTTP 500, thời gian phục hồi, lượng cảnh báo sinh ra) để đối chiếu với Trace Protocol đã thiết lập ở mục 3.4.1. 

## **Các loại kịch bản lỗi hỗ trợ (Fault Types):** 

- **Network Delay (Trễ mạng):** Bổ sung thời gian chờ nhân tạo (ví dụ: cộng thêm 3000ms) trước khi trả về response, nhằm kiểm tra cơ chế Timeout. 

- **Packet / Request Drop (Mất gói tin):** Chủ động ngắt kết nối (abort) hoặc trả về mã lỗi HTTP 503/504 để kiểm thử cơ chế Circuit Breaker và Retry. 

- **Exception Throw (Ném ngoại lệ ứng dụng):** Chủ động ném ra các ngoại lệ Runtime (như `NullPointerException` , `DatabaseConnectionError` ) để đánh giá khả năng handle exception và ghi log của ứng dụng. 

- **Resource Exhaustion (Cạn kiệt tài nguyên):** Chiếm dụng đột ngột CPU hoặc RAM tại các pod/container để kiểm thử khả năng auto-scaling và fail-over của hạ tầng.
